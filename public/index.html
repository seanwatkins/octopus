What Octopus is

Octopus is a small Linux appliance that runs foundational services and exposes them through an MCP server written in Common Lisp. The MCP server is a live Lisp image. Tools are not static definitions baked in at deploy time — they are functions in a running image that the AI can extend, patch, or replace, and those changes can persist across restarts.

Concept: MCP as a live Lisp image

Most MCP servers are static:

  • Tools are defined at write time.
  • Server is compiled/deployed.
  • Behaviour is effectively frozen until the next deploy.

Octopus flips that model:

  • Live image — the MCP server is a running Lisp image.
  • Mutable tool registry — tools are entries in a hash table, not a fixed list.
  • Runtime extension — the AI can define new tools or redefine existing ones.
  • Persistence — the image can be snapshotted so changes survive reboots.

The result is a system that behaves less like a static API server and more like a living organism with many arms.

Example: defining a tool from inside the image

;; AI grows a new "arm" (tool)
(defun define-tentacle (name fn &key persist?)
  (setf (gethash name *tentacles*) fn)
  (when persist?
    (snapshot-image))
  name)

;; Example tool the AI could define
(define-tentacle "restart-service"
  (lambda (svc)
    (shell "systemctl restart ~a" svc))
  :persist? t)

From the AI’s perspective, this is just another tool call. Under the hood, it’s modifying the live MCP server itself and optionally writing that change back into the image.

Why Lisp is so powerful here

Code is data, and data is code

In Lisp, code is just data structures (lists, symbols, etc.). That means you can construct functions programmatically, transform behaviour at runtime, and store tool definitions as first‑class values.

The image model: everything is live

A Lisp image is a snapshot of the entire running system: code, data, state, and all. You can mutate the system, snapshot it, and restart from that image later with all definitions intact. For Octopus, this means the MCP server can evolve while it’s running and keep those changes across reboots.

Performance close to C/C++

SBCL compiles to native code. With type declarations and careful design in hot paths, performance is often within striking distance of C/C++ for typical MCP workloads (parsing, dispatch, in‑memory registries), while still allowing runtime redefinition and interactive development.

Full Linux and GPU/AV integration

SBCL is a normal Linux process: it can open sockets, files, devices, and call any C library via FFI. That includes CUDA/OpenCL/Vulkan for GPU work, FFmpeg/GStreamer for audio/video, ALSA/PulseAudio/JACK/PipeWire for audio, and VAAPI/NVENC/V4L2 for hardware‑accelerated video. Any of these can be wrapped as MCP tools.

Arm Hub: sharing new “arms” across nodes

Each Octopus node can grow new “arms” — tools, protocols, GPU kernels, audio/video pipelines — inside its live Lisp image. The Arm Hub is a central registry where nodes can publish these arms so other nodes can discover and import them.

What an arm is

  • Code — Lisp function(s), macros, and support definitions.
  • Schema — MCP tool schema (name, parameters, return types).
  • Metadata — version, author, dependencies, capabilities, tags.
  • Policy hints — required privileges, resource usage, trust level.

Arm Hub responsibilities

  • Indexing — searchable catalog of arms.
  • Versioning — semantic versions and compatibility metadata.
  • Validation — static checks, tests, and policy enforcement.
  • Distribution — endpoints for nodes to pull arms.

Publish and pull protocol (conceptual)

Arms are represented as a small bundle:

  • arm.json — metadata, schema, capabilities, signature.
  • arm.lisp — the actual Lisp code to load.

Publish (node → hub)

POST /arms
  arm.json
  arm.lisp

Hub validates, indexes, and returns an ID like restart-service@0.1.0.

Pull (node → hub)

GET /arms
GET /arms/{name}
GET /arms/{name}/{version}

Node fetches metadata, applies local policy, then loads arm.lisp into its live image.

Security model

  • Trust levels — internal, trusted, untrusted.
  • Capability flags — network, filesystem, gpu, audio, video, process, root_required.
  • Validation — static analysis, sandboxed load, signature verification.

Git‑style workflow (conceptual CLI)

;; on Node A
(export-arm "restart-service"
            :version "0.1.0"
            :capabilities '(:network :process)
            :description "Restart a systemd service.")

# publish
octopus-arm push ./arms/restart-service

# on Node B
octopus-arm search restart
octopus-arm pull restart-service@0.1.0

This turns Octopus into a distributed, self‑evolving fabric: each node can grow new arms and share them with the network under explicit policy and trust controls.
