What Octopus is

Octopus is a small Linux appliance that runs foundational services and exposes them through an MCP server written in Common Lisp. The MCP server is a live Lisp image. Tools are not static definitions baked in at deploy time — they are functions in a running image that the AI can extend, patch, or replace, and those changes can persist across restarts.

Concept: MCP as a live Lisp image

Most MCP servers are static:

  • Tools are defined at write time.
  • Server is compiled/deployed.
  • Behaviour is effectively frozen until the next deploy.

Octopus flips that model:

  • Live image — the MCP server is a running Lisp image.
  • Mutable tool registry — tools are entries in a hash table, not a fixed list.
  • Runtime extension — the AI can define new tools or redefine existing ones.
  • Persistence — the image can be snapshotted so changes survive reboots.

Example: defining a tool from inside the image

;; AI grows a new "arm" (tool)
(defun define-tentacle (name fn &key persist?)
  (setf (gethash name *tentacles*) fn)
  (when persist?
    (snapshot-image))
  name)

;; Example tool the AI could define
(define-tentacle "restart-service"
  (lambda (svc)
    (shell "systemctl restart ~a" svc))
  :persist? t)

Why Lisp is so powerful here

Code is data, and data is code

Lisp represents code as native data structures. This enables programmatic function generation, runtime transformation of behaviour, and direct manipulation of tool definitions.

The image model: everything is live

A Lisp image is a snapshot of the entire running system: code, data, state, and all. You can mutate the system, snapshot it, and restart from that image later with all definitions intact.

The macro system: build new languages on the fly

Macros allow Lisp to extend itself. Octopus can define domain‑specific languages for tools, schemas, protocols, GPU kernels, or audio/video pipelines. These DSLs can be generated at runtime, enabling the AI to create new abstractions that become first‑class citizens in the system.

Native performance close to C/C++

SBCL compiles to native code. With type declarations and careful design in hot paths, performance is often within striking distance of C/C++. This means Octopus can handle protocol parsing, GPU dispatch, audio/video streaming, and other systems‑level tasks without sacrificing runtime flexibility.

Full Linux, GPU, and multimedia access

SBCL is a native Linux process with full access to system calls and C libraries. This includes CUDA, OpenCL, Vulkan, FFmpeg, GStreamer, ALSA, PulseAudio, JACK, PipeWire, VAAPI, NVENC, and more. Any of these can be wrapped as MCP tools and extended at runtime.

Why other languages can’t do this

Most languages force a trade‑off:

  • Python/Node: dynamic but slow, unsafe, and not persistent.
  • Go/Rust: fast but static — no runtime mutation.
  • Java: hot‑swap exists but is brittle and limited.

Lisp is the only environment that combines:

  • Runtime redefinition
  • Persistent images
  • Macro‑driven language extension
  • Native performance
  • Full OS and hardware access

Why Lisp makes Octopus possible

Octopus is not just a server — it is a live, evolving system. The AI can define new tools, patch behaviour, create new protocols, or extend the system in ways that persist across restarts. This is only possible because Lisp treats the running system as a living organism rather than a static binary. Octopus is effectively a modern Lisp Machine — embedded, networked, and AI‑driven.

GPU, Audio, and Video Capabilities

SBCL can interact with GPU compute, audio pipelines, and video systems the same way a C program can. This allows Octopus to expose GPU kernels, audio processing chains, or video transcoding pipelines as MCP tools that can be extended at runtime.

Arm Hub: sharing new “arms” across nodes

Each Octopus node can grow new “arms” — tools, protocols, GPU kernels, audio/video pipelines — inside its live Lisp image. The Arm Hub is a central registry where nodes can publish these arms so other nodes can discover and import them.
